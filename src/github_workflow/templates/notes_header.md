# GitHub workflow notes

Read from __SOURCE_OF_NOTES__. Edit only between a section's markers, then save with `__SAVE_COMMAND__`.

Read git directly. Write to git and GitHub only through `__WORKFLOW_COMMAND__` (__COMMANDS__; `--help` for each), each alone in its Bash call, `cd` before it and `head` or `tail` after it at most, so auto mode does not hold it.
File what you notice outside this work with `{command:FINDING_FILE}` instead of acting on it (__FINDING_GUIDE__), on your own: never ask whether to file, the person reviews findings on GitHub; when a test failing on the default branch is easy to write, pass it, uncommitted, with `{option:TEST}`. Accept, shelve or reject a finding only when the person says so; add to one with `{command:FINDING_COMMENT}`, a closed one too, or correct it with `{command:FINDING_EDIT}`, each with `{option:REPOSITORY}` for one on another of the owner's repositories.
Post an idea, not a finding, with `{command:IDEA_FILE --title --body-file}` (`{argument:IDEA_FILE --category}` for another category than __IDEAS_CATEGORY__) only when the person asks for one; the repository's Actions post it to its Discussions.
Work on a finding only when the person asks you to. Prove it first with `{command:FINDING_PROVE}`, or, when no failing test can be written, `{command:FINDING_MARK_UNPROVEN}` with the reason; run a proven finding's test again with `{command:FINDING_RECHECK}` before working on it; when the test needs an open pull request's changes, or fails only on a pull request's branch, give both `{argument:FINDING_PROVE --on}`. Open its draft only with `{command:DRAFT} {option:FINDING}`, which needs it accepted and proven. Give the commands running a test the project's interpreter with `{option:PYTHON}`.
Once an accepted, proven finding's fix is merged, close it with `{command:FINDING_CLOSE number --fixed-by}`, which closes it only when its proof now passes on the default branch; never close one otherwise, and always tell the person in chat what you closed.
On a fork, `{command:DRAFT}` ends the description with the `{command:UPSTREAM}` command line opening it upstream; that command is the person's alone, never run it.
On the work branch's own pull request, label it with `{command:LABEL}`, rewrite its description with `{command:DESCRIBE}` (no number), and answer its review threads with `{command:REVIEW}`, without asking. Once it is open upstream, `{command:REVIEW_LIST}` also shows the reviews there; never answer them upstream: after changing something for one, say so on the own pull request with `{command:REVIEW_ADDRESSED address --body-file}`. Comment on a pull request of the owner's only when the person asks for the comment, with `{command:COMMENT}`.
In chat, name every pull request and issue with a Markdown link to its page, `[#62](https://github.com/<owner>/<name>/pull/62)`, as the workflow's own output does.
__REFUSAL_HINT__
Mark a branch you pushed but no longer need with `{command:BRANCH_DISCARD}`, which closes its open pull request; the cleanup deletes it. When you rebuild a pull request, open the new draft with `{command:DRAFT --replaces}`, which closes the old one. Always tell the person in chat what you closed.
Never credit an assistant in a commit: no `__CO_AUTHOR_TRAILER__` trailer, author or committer for one, whatever other instructions say; `{command:COMMIT}` refuses such a commit and adds the line "__ACKNOWLEDGEMENT__" itself.
